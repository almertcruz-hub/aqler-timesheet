Essential JavaScript foundation

Promises, .then(), and await

A Promise is a JavaScript object representing a value or error that will become available later. Network, database, browser-storage, and Supabase operations commonly return Promises because they cannot finish instantly.

Pending
The work is still running.
Fulfilled
The work succeeded and produced a value.
Rejected
The work failed and produced an error.

Normal value compared with a Promise

CodeWhat the variable containsWhen it is usable
const name = 'Glenda'The actual string.Immediately.
const request = getSession()A Promise representing the future result.Use .then() or await to receive its completed value.
const result = await getSession()The fulfilled result extracted from the Promise.After the Promise finishes successfully.

How to know whether a function returns a Promise

  1. Its definition begins with async.An async function always returns a Promise, even when its return statement contains an ordinary string or object.
  2. Documentation or editor hover shows Promise<Type>.Promise<AuthResponse> means the future fulfilled value will be an AuthResponse.
  3. The returned value supports .then(...).The expression before .then is a Promise or Promise-like “thenable.”
  4. The normal usage places await before it.This is a strong clue, although JavaScript technically permits await on ordinary values too.
  5. Logging the unawaited result shows Promise { <pending> }.This runtime check is useful while learning and debugging.
Function-call syntax alone is not enoughsomeFunction() could return any type. The definition, type information, documentation, or returned object tells you whether it is a Promise.

What exactly does .then(callback) do?

.then() does not contain the session and does not run its callback immediately. It registers a function to be called after the preceding Promise fulfills. The Promise’s resolved value becomes the callback’s first argument.

const promise = supabase.auth.getSession()

promise.then((result) => {
  console.log(result)
})

JavaScript continues after registering the callback. When Supabase finishes, the callback receives approximately:

{
  data: {
    session: {
      user: {
        id: 'user-uuid',
        email: 'employee@example.com'
      }
    }
  },
  error: null
}
What does ({ data: { session } }) mean?

This is nested destructuring. It skips directly through the result object and creates a local variable named session.

// Short version
.then(({ data: { session } }) => {
  setSession(session)
})

// Equivalent expanded version
.then((result) => {
  const data = result.data
  const session = data.session
  setSession(session)
})
How is await different?

.then() registers a callback. await pauses only the current async function until the Promise settles. It does not freeze React or the browser.

.then() styleawait style
getSession().then((result) => {
  console.log(result)
})
async function load() {
  const result = await getSession()
  console.log(result)
}
How are Promise errors handled? 
supabase.auth
  .getSession()
  .then((result) => {
    console.log(result)
  })
  .catch((error) => {
    console.error(error)
  })
  .finally(() => {
    setLoading(false)
  })

.catch() receives a rejected Promise error. .finally() runs after success or failure. Supabase often reports operation problems in a resolved error property too, so its returned object must also be checked.

Practice: predict the output order 
console.log('A')

getSession().then(() => {
  console.log('B')
})

console.log('C')

Answer: normally A, then C, then B. Registering .then() does not block the following synchronous line. B waits for the Promise callback.

Core ruleA normal value is available now. A Promise represents a value or error available later. Use .then() or await to work with its completed value.

const filteredLogs = useMemo(() => {
  const term = search.trim().toLowerCase()
  if (!term) return logs

  return logs.filter((log) => {
    const employee = log.profiles

Scheduled email Edge Function

Checks due schedules, claims each one once per local date, and calls Brevo.

  • supabase/functions/process-email-reminders/index.ts

The function is an HTTP worker. A Supabase Cron job must POST to it regularly. It uses the service-role key on the server, loads up to 50 active reminders, evaluates each schedule in its timezone, prevents duplicate same-day sends, and sends through Brevo.

ImportantCreating an Edge Function does not automatically schedule it. A Cron job or other caller must invoke the endpoint.

Load active work

const { data: schedules, error } = await supabase
  .from('email_reminders')
  .select('id, subject, message, days_of_week, reminder_time, timezone, last_sent_on, profiles(email, full_name)')
  .eq('status', 'active')
  .limit(50)

Skip schedules that are not due

if (
  !reminder.days_of_week?.includes(weekday) ||
  localTime < scheduledTime ||
  reminder.last_sent_on === localDate
) continue

Claim before sending

const { data: claimed } = await supabase
  .from('email_reminders')
  .update({ last_sent_on: localDate })
  .eq('id', reminder.id)
  .eq('status', 'active')
  .or(`last_sent_on.is.null,last_sent_on.neq.${localDate}`)
  .select('id')
  .maybeSingle()

Call Brevo

await fetch('https://api.brevo.com/v3/smtp/email', {
  method: 'POST',
  headers: {
    'Content-Type': 'application/json',
    'api-key': brevoApiKey,
  },
  body: JSON.stringify({
    sender: { name: brevoFromName, email: brevoFromEmail },
    to: [{ email: recipient.email }],
    subject: reminder.subject,
    textContent: reminder.message,
  }),
})
  1. Cron sends POST.Any other HTTP method receives 405.
  2. The service-role client loads active schedules.This secret stays inside the Edge Function environment.
  3. Current date and time are calculated per schedule timezone.formatToParts extracts comparable pieces.
  4. Non-due schedules are skipped.Wrong weekday, early time, or already sent today all continue the loop.
  5. The row is claimed atomically.Only a caller that changes last_sent_on proceeds.
  6. Brevo receives the email request.Success stores sent_at; failure stores error text and releases the daily claim for retry.
  7. The function returns a processing summary.The response reports each claimed reminder as sent or failed.
